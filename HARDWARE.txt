RAY POKERI (1990) - hardware notes
==================================

Worked out from the game ROM, the RAY service manuals (Huolto ja korjaus,
Toimintaselostus) and testing in the emulator. Things marked "?" are
guesses.


Main board
----------
  CPU        Motorola 68000, 8 MHz
  Video      Hitachi HD63484 ACRTC graphics processor, 3 MHz clock (2CLK:
             a 12 MHz crystal divided by 2 twice in logic, schematics
             page 1), 4 bits per pixel, 608 x 292 visible, 16 fixed colours
             (video board 5501; the 5502 has a palette chip, see below)
  I/O        3 x MC6821 PIA, MC6850 ACIAs (serial), MC68681 DUART (optional)
  Sound      AY-3-8910 on the light/sound board, 1 MHz clock, driven
             through PIA1
  NVRAM      battery-backed RAM + MK48T02-style clock
  Display    7-segment LED for service codes, on PIA3


Memory map
----------
The board decodes only address lines A0-A19, so everything repeats every
1 MB. (The ROM has a bug at 0xD05A that only works because of this mirroring.)

  000000-03FFFF   program ROM, 256 KB (four 64 KB EPROMs, see below)
  040000-04FFFF   RAM, 64 KB
                    043800-043FFF battery backed
                    043FF8-043FFF clock registers (MK48T02 layout)
                    048B00 = value of A6 (global data base)
  0C0000          MC68681 DUART (level 2 autovector) - not emulated
  0F6000          HD63484 address register (write) / status (read)
  0F6002          HD63484 data
  0FB002/3        ACIA1 control/data: coin processor link
  0FB006/7 ...    ACIA2-5 at FB000 + 4n + 2
  0FB014-017      PIA1  light/sound board
  0FB018-01B      PIA2  buttons, door, service switches
  0FB01C-01F      PIA3  7-segment display, watchdog, misc inputs

The HD63484 is on the upper byte lane. A byte access addresses one register
byte: an even register address is the high byte, an odd one the low byte.
With bit 7 of the address set, the address steps by one byte per access.
The command FIFO (address 0) pairs two bytes into a word.


Video boards 5501 and 5502
--------------------------
The cabling diagram of the Norwegian POKER/RKA (POKER_RKA.pdf page 1)
shows the game board "Spelprocessor 5003-2" with "Monitorns styrenhet
PCB 5501-0", the video board the emulator has by default: 512K words of
video memory and 16 fixed colours, dimmed by the ACRTC's DCR outputs.

Page 2 of the same file is its successor, "Videomonitorin ohjain II"
(PIK-5502-0, 1990-91). The same ACRTC (IC44), clocked through RAY's own
logic chip RAY7115 (IC46, 44 pins, a 24 MHz crystal; it also makes the
dot clock, the DRAM timing and the sync), plus:
  - 1M words of video memory (four RAS banks)
  - IMS G176 palette DAC (IC45) at 0E0000: 256 colours of 6 bits per
    gun; registers at +0 (write address), +2 (red, green, blue in turn),
    +4 (pixel mask), +6 (read address). Its P0-P3 are the pixel
    (LEV, RED, GRE, BLU), P4/P5 pulled high, P6/P7 latch MAD16/MAD17.
  - MC68681 DUART (IC17) at 0C0000, register n at 0C0000 + n: port A
    with RTS/CTS and +12 V to J4, port B and the spare inputs and
    outputs to J5. For the central computer link (GAME.txt section 10).
  - 32 KB static RAM (IC28) at 0D0000

The program supports both. At start (ROM 0x5B9C) it writes 3456 to video
memory word 30000 and BCDE to B0000: on a 5501 they are the same word.
On a 5502 it then
  - loads the G176 with its own palette (ROM 0x5D76, 64 colours = four
    sets of 16, written four times to fill 256) and sets up the DUART
  - tests both at start-up (ROM 0x16E1C): the DUART's interrupt vector
    must read 0F (fault 17 = IC17 otherwise), the RAM must keep a long
    word (fault 28 = IC28)
  - does the screen saver with the G176 pixel mask instead of the DCR
    (ROM 0x5B3A): brightness 63 -> mask CF (set 0, the normal colours),
    59 -> DF (set 1, a little dimmer), 35 -> EF (set 2: blue turns gold,
    red magenta), 29 -> FF (set 3)

--board 5502 emulates it: the RAM, the G176 and the DUART as far as the
start-up test needs (always ready to send, never receives anything).

Program ROM
-----------
The four EPROMs on the main board (PCB 5003), 64 KB each, one after the
other. The bracketed number on a label is the 16-bit sum of the chip's bytes
(--list-roms checks these). Each chip is one file in roms/:

    address      chip  label             sum   contents
    00000-0FFFF  IC30  6457-7.7 J        A8EF  program ("romgame"), reset vectors
    10000-1FFFF  IC38  6458-7.7 J        14E2  program
    20000-2FFFF  IC34  6458-7.7 J        01C5  program, linked 27.09.94
    30000-3FFFF  IC43  8460-1.1 J1/100   -     game parameters ("gamepara"), 10.10.94

The first three chips hold one OS-9 module, "romgame" (0x00400-0x276FE):
the whole program, the poker code included (the double-up at 0x18380, for
example, is in IC38). IC43 holds only the module "gamepara" (0x30000-
0x3640, the rest of the chip is empty): the parameter block of GAME.txt
section 8 (pay table, limits, all screen texts) and the sound data.

So a version with other prizes or in another language is another IC43 on
the same program. The 200 MK poker (game 7907-2.0, module "g200para", 16.04.93, ROM set
pokeri-7907-2.0) differs only in IC43. Another game, such as Noppa,
would need its own program chips as well.

OS-9 is a small real-time operating system from Microware, first for the
6809 (1979-80) and then the 68000 (OS-9/68000), common in embedded and
industrial systems and in Philips CD-i. It has nothing to do with Sun
(SunOS) or Apple's Mac OS 9. The ROMs hold no OS-9 kernel (no "OS-9",
"Microware" or "kernel" anywhere): the game runs straight on the
hardware from its own start-up code. RAY's programmers most likely wrote
it in C on an OS-9 development system and packed it into OS-9 modules:
  - each module has the OS-9/68000 header: sync 4AFC, size, name, type
    01 (program), language 01 (68000 code), header parity, and a 24-bit
    CRC at the end, which the start-up self test checks (pyray/
    paramrom.py recomputes both when it builds an IC43)
  - Microware C keeps the global variables relative to register A6,
    which is why the code is full of -30991(a6) and jsr -27758(a6), and
    why these notes name RAM as A6-nnnnn

The program can also run from RAM, which must be how it was developed
(loaded into a development board, probably from the OS-9 system). The
reset code (ROM 0x217E) writes 0 over a long word of its own program
(0x24EA) and reads it back. In ROM the write does nothing. In RAM it
sticks, and then everything moves up by 0x70000: the supervisor stack
0x40B00 -> 0xB0B00, the user stack 0x40700 -> 0xB0700 and A6 (all the
global variables) 0x48B00 -> 0xB8B00, so the working RAM is at 0xB0000-
0xBFFFF instead of 0x40000-0x4FFFF. The same test again (0x25A4) puts
the parameter module at 0xBC000 instead of 0x30000 (pointer at
A6-29530) and patches handler addresses into its own image (0x28FA).
The emulator ignores writes to ROM, like the real board.


Interrupts
----------
A priority encoder gives vectors 64-71 on level 4:
  64  int0  HD63484 (command FIFO refill, game feeds the chip from a queue)
  67  int3  100 Hz mains phase, via PIA1 CB2
  69  int5  ?
  70  int6  PIA1 CA1
  71  int7  ACIA1, coin processor
  level 2   MC68681 DUART (autovector)
  level 7   NMI: PIA3 CB1 = power failing, PIA3 CB2 = watchdog warning

The game runs its tasks in user mode; interrupts switch to the supervisor
stack.


Watchdog
--------
Kicked by a pulse on PIA3 PB7 or by the 68000 RESET instruction (which
also resets the peripherals). After about 0.4 s without a kick it raises
the warning NMI, and about 100 ms later it resets the CPU. The boot
self-test deliberately stops kicking it and checks that the reset
happens (more than 25 ms later), otherwise it shows fault 04. The
software also stops kicking when a task runs for over 0.2 s.


PIA1 - light/sound board
------------------------
  Port A          data bus D0-D7
  PB0             /WRITE
  PB1             MODE (also AY BC1)
  PB2             STROBE
  PB7             SSEL (AY BC2)
Lamp data is latched on a rising MODE edge and moved into lamp latch
(data & 7) on a falling STROBE edge. There are 3 latches = 24 outputs.
Latch 2 bit 7 drives AY BDIR, and latch 2 bit 3 (lamp bit 19) is VOL, the
sound volume switch (below); the other 22 are lamps. (The latch chips'
inputs are not wired in bit order: VOL is pin 16 of IC2 on the schematic.)
  CA1             interrupt (vector 70)
  CB2             100 Hz mains phase (vector 67)

Sound (light/sound board schematic, page 2): the AY-3-8912 has its own
1 MHz crystal. Each of its three outputs has 1k to ground and 10k to a
common mixing point, which goes through 27k and the volume trimmer P1 (1k)
to a TDA1011A amplifier at 12 V, and through 1000 uF to the speaker. When
VOL is on, transistor Q13 shorts the mixing point to ground through 1k
(R16), which leaves 1/4 of the level (-12 dB). The game keeps it on (quiet)
and turns it off (loud) for the doubling music, the lost-double "kosh" and
the card-holding sound; ROM 0x1D12 sets it (0 = quiet, 1 = loud). Most of
the sounds use the chip's envelope generator, which always plays at full
level, so the chip's own volume registers couldn't have done this.


PIA2 - buttons and switches (all active low)
--------------------------------------------
  PA0  JAKO (deal)            PB0  VALITSE 3
  PA1  VOITONMAKSU (collect)  PB1  VALITSE 2
  PA2  PANOS (bet)            PB2  HUOLTO (service)
  PA3  SUURI (big)            PB3  SRVC1
  PA4  PIENI (small)          PB4  SRVC2
  PA5  TUPLAUS (double)       PB5  VALITSE 1
  PA6  VALITSE 5              PB6  door switch (0 = door open, "OVI AUKI")
  PA7  VALITSE 4              PB7  +12 V guard (0 = power OK)


PIA3 - misc
-----------
  PA0, PA1        cable sense? (held 0)
  PA2-PA5         K13-K16 (K16 opens the test menu, TESTI 0-15)
  PB0-PB6         7-segment display segments a-g
  PB7             watchdog kick
  CB1             power fail (NMI)
  CB2             watchdog warning (NMI)


Video (HD63484)
---------------
The screen is three stacked horizontal screens, all 152 words (608 pixels)
wide in memory:
  upper   40 lines   (R8C height, RC2 width, RC4/RC6 start address)
  base   222 lines   (R8A, RCA, RCC/RCE)
  lower   30 lines   (R8E, RD2, RD4/RD6)
OMR = CD28: master, started, display priority, GAI = 4 words per display
cycle, interleaved access (drawing shares memory cycles with the display).
Command execution times are in the user's manual, p. 173. The game waits
for the chip (FIFO ready / command end), so drawing speed affects how fast
some animations run. Arc direction bit C=1 means clockwise, with Y up.

Plus a window (R90-R96 position/size, RDA-RDE memory) used for the card
sliding in while it's dealt.

DCR (R06):
  bits 15-8   screen enables (window = bits 9-8)
  bits 5-0    colour attenuation outputs to the RGB DAC; the game clears
              bit 2 to tint the screen yellow while idle
At startup the game draws the card faces and symbols in off-screen memory
and later block-copies them into place.


Coin processor (PCB 5002) - serial link on ACIA1
------------------------------------------------
Source: Toimintaselostus, Rahakoneiston ohjain 5002, section 3.2.4.
  Frame        1-3 data bytes (bit 7 clear) + check byte
               check = (~sum(data)) | 0x80 (also marks end of frame)
  Control      30 ENQ, 00/40 ACK (toggle 0/1), 28/68 NAK, 50 EOT
  Toggle       bit 6 of the first byte alternates between messages;
               the first message of each session has toggle 0
  Session      opener sends ENQ, other side answers ACK, opener sends
               data frames (each ACKed), then EOT
Some messages:
  01 07 00     coin unit cold start          01 79 00  self tests OK
  01 44 00     hopper empty                  09 n      test request
  31           parameter request/answer      03        coin in (channel 1)
  24 n         pay n coins (hopper 1)        05        one coin paid


Bookkeeping RAM ("kassamuisti")
-------------------------------
Three copies (pointers at A6-31532, -31528, -31524) of 18-byte records
(16 data bytes + CRC-16). ROM routine 0xDC70 recomputes a record's CRC
and copies it to the other two copies.
  [0]     money held = [12] + [18] + [22]
  [4]     money in
  [12]    payout reserve (must cover the biggest win, otherwise
          "P3 89 voitonmaksureservi riittämätön")
  116     PELIT (credits)
  120     VOITOT (wins)
  126     word: closure code, low byte FF = machine open
          e.g. 0x1384 = "P3 84 voitonmaksukoneet tyhjiä" (hoppers empty)
Boot check (ROM 0xB27C): if the sums don't match, "P3 00 kassavika".

Fault codes are kept in 10 slots at A6-30831 and shown on the 7-segment
display; the code list is in Huolto ja korjaus, page 15.
